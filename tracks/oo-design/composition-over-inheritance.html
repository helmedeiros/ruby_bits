Composition over inheritance

{% capture lesson_body %} ## Composition over inheritance ### Two ways to share behavior Suppose you're building a checkout flow with several pricing strategies — fixed price, taxed, volume-discounted. There are two common ways to share behavior: **Inheritance**: `TaxedOrder < Order`. Every taxed order *is* an order, with tax behavior added. **Composition**: `Order` holds a *pricer*. The pricer calculates the total. Swap the pricer and the calculation changes; the Order doesn't. Both work for small examples. Composition tends to scale better. ### Why composition usually wins Inheritance is rigid: an object is either a `TaxedOrder` or not, forever. If next month you need "taxed AND volume-discounted", you're stuck building a combinatorial tower of subclasses (`TaxedDiscountedOrder`, `TaxedDiscountedPrimeOrder`, …). Composition is flexible: an `Order` can hold *any* pricer — fixed, taxed, discounted, or one you write today that combines two others. The structure of `Order` doesn't change. ### A concrete example ```ruby class Order def initialize(items:, pricer:) @items, @pricer = items, pricer end def total @pricer.total(@items) end end class FixedPricer def total(items) items.sum { |i| i[:price] } end end class TaxedPricer def initialize(rate); @rate = rate; end def total(items) items.sum { |i| i[:price] } * (1 + @rate) end end ``` `Order` only knows it has *a pricer* — anything that responds to `total(items)`. The pricer can be as simple or as smart as you like. You can also compose pricers (e.g. a `DiscountedPricer` that wraps another pricer). ### Has-a vs is-a The shorthand test: ask "is this new class a more specific version of the parent, or does it just *have* one of those?". - `Cat` *is a* `Animal`. → inheritance is fine. - `Order` *has a* pricer. → composition. - `Car` *has an* engine. → composition. - `RoadBike` *is a* `Bicycle`. → either could work; composition often wins long-term because it stays flexible. ### When to still reach for inheritance Inheritance is great when you have: - A real **is-a** relationship. - A small (2-4) **closed** set of subclasses that won't multiply. - A clear template method or shared algorithm. Outside those cases, composition usually keeps your design friendlier to change. {% endcapture %} {{ lesson_body | markdownify }}
