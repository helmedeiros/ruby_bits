Inject collaborators

{% capture lesson_body %} ## Dependency injection ### What's a dependency, anyway? A class **depends on** another whenever it knows *something specific* about it. There are four common kinds of dependency: 1. **The other class's name** — `Sms.new` mentions `Sms`. 2. **The other class's message names** — calling `send_to` means you depend on that method existing. 3. **The argument order** — `send_to(phone, body)` ties callers to that order. 4. **The argument types** — `send_to(Phone.new(...), ...)` ties callers to the `Phone` class. Each dependency is a *risk*: if anything about the other class changes, your class might break. ### A tightly coupled example ```ruby class OrderConfirmation def deliver(order) Sms.new.send_to(order.phone, "order #{order.id} confirmed") end end ``` Count the dependencies on the `Sms` class alone: - Knows the **name** `Sms`. - Knows it responds to `new` with no arguments. - Knows it responds to `send_to(phone, body)`. - Knows the argument **order**. If anyone renames `Sms`, changes its constructor, or reorders the arguments — this class breaks. ### The fix: pass it in Instead of constructing the collaborator inside, **accept it as an argument** (usually through `initialize`): ```ruby class OrderConfirmation def initialize(channel: Sms.new) @channel = channel end def deliver(order) @channel.send_to(order.phone, "order #{order.id} confirmed") end end ``` Now `OrderConfirmation` only knows it has *something that responds to `send_to(phone, body)`*. The `Sms` class name appears in the **default**, not in the body of the method — so callers can swap in any other channel without touching this class: ```ruby OrderConfirmation.new(channel: Email.new) OrderConfirmation.new(channel: PushNotification.new) OrderConfirmation.new(channel: FakeChannel.new) # for tests ``` ### Why this matters - Tests get easier — pass a fake `channel` that just records calls. No SMTP, no network. - You can add new channels (push, slack, webhook) without opening `OrderConfirmation`. - The single test of "deliver builds the right message body" doesn't care which transport runs underneath. ### Rule of thumb When you find yourself writing `SomeClass.new(...)` inside another class, ask: **could the caller decide which class to use?** If yes, inject it. {% endcapture %} {{ lesson_body | markdownify }}
