Extract a collaborator

{% capture lesson_body %} ## Pulling responsibilities apart So `Invoice` does too much. How do you fix it? The refactor pattern is: **extract a class** for each extra responsibility, then have the original class **delegate** to it (or to its caller, if neither object should own the new one). ### Step 1: Identify the seams From the previous lesson, the three jobs were: money, PDFs, mail. So you'll have three classes. `Invoice` keeps the money. A new `InvoiceRenderer` owns PDFs. A new `InvoiceMailer` owns delivery. ### Step 2: Name them by responsibility A useful tactic is to pick a noun for each new class that describes its **single job**: ```ruby class InvoiceRenderer def initialize(invoice) @invoice = invoice end def to_pdf # render the PDF using @invoice's data end end class InvoiceMailer def initialize(invoice, transport: SMTP) @invoice, @transport = invoice, transport end def deliver_to(customer) # build, attach PDF, send via @transport end end ``` Each new class holds the original invoice as a collaborator and asks it for the data it needs (the `total`, the line items). Notice neither of them mutates `Invoice` — they only *read* it. ### Step 3: Slim down the original With the extracts in place, `Invoice` shrinks back to just its job: ```ruby class Invoice def initialize(customer, lines) @customer = customer @lines = lines end def total @lines.sum { |l| l[:qty] * l[:price] } end end ``` ### Why this is better - The class names tell you exactly what to expect. - Tests for `Invoice` no longer need a PDF library. - You can run `InvoiceRenderer` against any object that responds to `total`, `line_items`, etc. — that's the seed of a *duck type* (you'll meet that idea later). ### A working example to refactor The next activity gives you a `Notifier` that formats AND delivers. You'll extract the formatting into its own class so either responsibility can change without dragging the other along. {% endcapture %} {{ lesson_body | markdownify }}
