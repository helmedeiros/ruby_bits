attr_reader, attr_writer, attr_accessor

{% capture lesson_body %} ## attr_accessor, attr_reader, attr_writer Writing `def balance; @balance; end` (and the matching `=` writer) for every instance variable gets tedious fast. Ruby gives you three shorthands that generate these methods for you. ### `attr_reader` — read-only Generates a getter: ```ruby class Account attr_reader :balance def initialize(balance) @balance = balance end end a = Account.new(100) a.balance # => 100 a.balance = 50 # NoMethodError — no setter ``` Use this when callers should be able to *see* the value but not change it directly. Mutation should happen through deliberate methods (`deposit`, `withdraw`), not by overwriting state. ### `attr_writer` — write-only Generates a setter: ```ruby class Logger attr_writer :level end l = Logger.new l.level = :debug # works l.level # NoMethodError — no getter ``` Used much less often than `attr_reader`. ### `attr_accessor` — both Both getter and setter: ```ruby class User attr_accessor :name end u = User.new u.name = "alice" u.name # => "alice" ``` ### Use the strictest one that works If callers should only *read*, use `attr_reader`. If they need to *write*, use `attr_accessor`. Don't reach for `attr_accessor` reflexively — it gives callers permission to change state, which spreads responsibility. ### Multiple at once All three accept several symbols: ```ruby attr_reader :name, :email, :role attr_accessor :active, :verified ``` ### Pitfall: inside the class, prefer the accessor Once you have `attr_reader :balance`, code inside the class can call `balance` instead of `@balance`. The advantage: if you later change how `balance` is computed (e.g. add caching, or compute from other fields), you only change the `balance` method — every internal user follows along. {% endcapture %} {{ lesson_body | markdownify }}
