Mixin with include

{% capture lesson_body %} ## Mixin with `include` A module can carry methods for *other* classes to use. When a class `include`s a module, the module's methods become **instance methods** on that class. ### Basic example ```ruby module Greetable def greet "hi, I'm #{name}" end end class User include Greetable attr_reader :name def initialize(name); @name = name; end end class Robot include Greetable attr_reader :name def initialize(name); @name = name; end end User.new("alice").greet # => "hi, I'm alice" Robot.new("R2D2").greet # => "hi, I'm R2D2" ``` Both `User` and `Robot` get `greet` without any inheritance relationship. The module describes a **role** (anything that can greet) rather than a specific class. ### Why use it? - Share behavior across **unrelated** classes — no need to invent a common parent just to share code. - Keep classes small. A class with five mixins is often clearer than one with fifty methods. - **No diamond problem.** Ruby resolves the order deterministically through the ancestor chain. ### Where modules sit in the ancestor chain ```ruby User.ancestors # => [User, Greetable, Object, Kernel, BasicObject] ``` Notice `Greetable` is between `User` and `Object`. When you call `greet`, Ruby walks this chain top to bottom and stops at the first match. ### Modules can rely on host methods In the example, `Greetable` calls `name` — a method `User` and `Robot` provide. The module describes a **contract**: "I'll give you `greet` if you give me `name`." This is duck typing again. ### `include` vs `extend` - `include` adds the module's methods as **instance** methods. - `extend` adds them as **class** (singleton) methods. Next lesson covers `extend`. {% endcapture %} {{ lesson_body | markdownify }}
