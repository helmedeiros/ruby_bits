Hook methods

{% capture lesson_body %} ## Hook methods Ruby gives a class a chance to **react** when something happens in its lifecycle — when it's inherited, when a module gets included, when an object is created. These reactions are called **hook methods**. ### `inherited` — runs when a subclass appears ```ruby class Plugin def self.inherited(subclass) puts "registering #{subclass}" @subclasses ||= [] @subclasses << subclass end def self.subclasses @subclasses ||= [] end end class Logger < Plugin; end # prints "registering Logger" class Notifier < Plugin; end # prints "registering Notifier" Plugin.subclasses # => [Logger, Notifier] ``` Useful for registries, factory tables, or any "auto-discover all subclasses" pattern. ### `included` and `extended` — runs when a module is mixed in ```ruby module Trackable def self.included(base) puts "#{base} now Trackable" end end class User include Trackable # prints "User now Trackable" end ``` This is the bedrock under `ActiveSupport::Concern` — when you include the module, hook code runs in the *including* class's context. Common use: also `extend` a `ClassMethods` submodule so the host class gains class-level helpers. ### Why hooks help Hooks let a parent (or module) react *automatically* to being used. No subclass has to remember to "register itself". The wiring happens by definition, not by call. ### Pitfall: surprise side effects Hooks make magic look easy, but the magic is invisible at the call site. Someone reading `class Logger < Plugin` sees no registration code — yet `Logger` now appears in a global list. Use hooks sparingly and document them in the parent. {% endcapture %} {{ lesson_body | markdownify }}
