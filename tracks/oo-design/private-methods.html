Private methods

{% capture lesson_body %} ## Private methods By default, every method you define in a Ruby class is **public** — any code with a reference to the object can call it. That's a lot of surface. The `private` keyword shrinks the public interface to just what you want callers to use. ### Marking methods private Place `private` on its own line; everything defined after it (until another visibility keyword) is private: ```ruby class Order def confirm! return false unless valid? mark_confirmed true end private def valid? !total.zero? && customer end def mark_confirmed @confirmed_at = Time.now end end ``` Now `order.confirm!` works from outside, but `order.mark_confirmed` raises `NoMethodError`. Internal helpers stay internal. ### Why bother? - **Smaller public surface** = fewer ways callers can misuse the object. - **Freedom to refactor**: you can rename or delete a private method confidently — no external code can depend on it. - **Clearer reading**: the public methods at the top tell you what the object *does*; the private ones below show *how*. ### `protected` (rare) Ruby also has `protected`. It allows calls between instances of the same class but blocks external callers. Useful when objects compare themselves to siblings (`<=>`, `==`). For everyday code, `private` is what you reach for. ### Pitfall: `self.method` inside the class You **cannot** call a private method with an explicit `self.` (with one exception for `self.attr=` setters in Ruby 2.7+). Inside the class, just call the method without a receiver. ```ruby private def valid?; true; end # in another method of the same class: valid? # works self.valid? # NoMethodError: private method ``` {% endcapture %} {{ lesson_body | markdownify }}
