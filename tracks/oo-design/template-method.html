Template method

{% capture lesson_body %} ## Template method ### The idea Inheritance is most useful when a family of classes shares the **shape** of an algorithm, but differs in one or two specific steps. The Template Method pattern captures this: the parent defines the algorithm and reserves "slots" — methods that subclasses must implement. The parent guarantees the structure; the subclass fills in the details. ### Concrete example ```ruby class Report def render "#{header}\n#{body}\n#{footer}" end def header; "REPORT"; end def footer; "-- end --"; end def body raise NotImplementedError, "#{self.class} must implement #body" end end ``` Notice three things: 1. `render` defines the **algorithm**: header, body, footer. 2. `header` and `footer` have **safe defaults** that subclasses can keep or override. 3. `body` is **unimplemented** — it raises. This is the "contract": "I, the parent, won't render unless my child tells me what the body is." ### A subclass ```ruby class SalesReport < Report def body "sales were up 12%" end end SalesReport.new.render # => "REPORT\nsales were up 12%\n-- end --" ``` The subclass only had to provide `body`. It inherited the algorithm structure plus the default header/footer for free. ### Why `raise NotImplementedError`? Without the raise, a subclass that forgot to implement `body` would silently return `nil`, and your report would render weirdly with a blank line in the middle. With the raise, the mistake is caught loudly: "you forgot to implement body". ### When to reach for inheritance Use inheritance only when the relationship is genuinely "*is-a*": `SalesReport` *is a* `Report`. If you're using it just to share code, prefer composition (next module) or a module (later). ### Naming heuristic You can usually spot template-method opportunities by looking at a method that has three to five small steps and one or two of those steps vary by use case. Pull the framework into a parent, hand the variable steps to subclasses. {% endcapture %} {{ lesson_body | markdownify }}
