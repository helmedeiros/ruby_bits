Find the duck

{% capture lesson_body %} ## Duck typing ### The dictionary definition > If it walks like a duck and quacks like a duck, it's a duck. In static languages, you declare types — `String`, `Integer`, `Customer`. In Ruby, what matters at runtime is **what messages an object responds to**, not what class it belongs to. Any object that responds to `each` can be iterated; any object that responds to `to_s` can be printed. That's duck typing. ### What it looks like Compare two ways of writing the same code. **Without duck typing**, you switch on class: ```ruby def render(report) case report when DailyReport then DailyRenderer.new.render(report) when WeeklyReport then WeeklyRenderer.new.render(report) when MonthlyReport then MonthlyRenderer.new.render(report) end end ``` Every new report type means editing `render`. **With duck typing**, ask each report to render itself: ```ruby def render(report) report.render end ``` Now `DailyReport`, `WeeklyReport`, `MonthlyReport` each implement `#render` differently. Adding a new report type means adding a new class with a `#render` method — no edits to the caller. ### Smell: `case … when SomeClass` A `case` (or `if`) that switches on `is_a?` or class names is almost always a duck type waiting to be extracted. Each branch can become a method on the object itself. ### Recognizing ducks Look for clusters where: - Multiple classes implement the **same method** with the same shape (`#render`, `#price`, `#deliver`). - Callers have to **branch** based on which class came in. - You feel the urge to add an `if` to support a new type. Each cluster is a duck type. Name it (e.g. "Printable") and let polymorphism do the work. {% endcapture %} {{ lesson_body | markdownify }}
