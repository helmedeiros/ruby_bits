Open / Closed

{% capture lesson_body %} ## Open / Closed *"Open for extension, closed for modification."* A class should be designed so that **new** behavior can be added without **editing** the existing code. You add — you don't reach inside. ### The smell When every new feature means cracking open the same class and adding another `case`/`if`, the class is failing the Open/Closed test: ```ruby class TaxCalculator def tax(item) case item.country when "BR" then item.price * 0.15 when "US" then item.price * 0.08 when "DE" then item.price * 0.19 # next month: add JP, FR, IT, ES, … end end end ``` Every new country forces a change to `TaxCalculator`. The class has one job (compute tax), but its definition keeps growing. ### The cure: extend, don't modify Push the country-specific logic *out* of `TaxCalculator` and into small per-country objects. Then `TaxCalculator` only dispatches — it doesn't decide. ```ruby class BrazilianTax def for(item); item.price * 0.15; end end class UsTax def for(item); item.price * 0.08; end end TAX_RULES = { "BR" => BrazilianTax.new, "US" => UsTax.new } class TaxCalculator def initialize(rules: TAX_RULES); @rules = rules; end def tax(item); @rules.fetch(item.country).for(item); end end ``` Adding Japan tomorrow is just a new class + one row in the table — no edits to `TaxCalculator`. The dispatcher is **closed** to modification but the system is **open** to extension. ### Tools that help - **Polymorphism** — multiple classes responding to the same message. - **Composition + injection** — pass the strategy in. - **Tables / registries** — a hash from key to handler. - **Hook methods** — let parents register child behavior. ### When the rule does NOT apply Don't anticipate every possible axis of change. You can't make code open to *every* future change without paying complexity now. The rule kicks in when you've **seen the same edit twice**. The third time, refactor toward extension. {% endcapture %} {{ lesson_body | markdownify }}
