Spotting an SRP violation

{% capture lesson_body %} ## Single Responsibility Principle (SRP) ### What's a class for? A class bundles **data** and **behavior** that belong together. The longer it lives, the more pressure it feels to grow. New requirements arrive. People add methods. Before you know it, a single class does five unrelated things. The Single Responsibility Principle is a check against that growth: **a class should have one reason to change**. Said another way — if you can describe what the class does in one sentence without using "and" or "or", you're probably fine. If you need conjunctions, the class is doing too much. ### A class that does too much Look at this `Invoice`: ```ruby class Invoice def initialize(customer, lines) @customer = customer @lines = lines end def total @lines.sum { |l| l[:qty] * l[:price] } end def to_pdf # render headers, draw the table, embed the company logo, # ship the bytes to a file end def email_to_customer # build an HTML body, attach the PDF, open an SMTP socket, # talk to the mail server end end ``` What does it do? It **calculates totals AND renders PDFs AND sends mail**. Three jobs, three reasons to change: 1. The pricing rules change (tax law, discounts). 2. The marketing team wants a new PDF style. 3. Operations switches SMTP providers. Worse, those reasons share **no logic**. Touching the PDF renderer to add a logo shouldn't risk breaking the total. But here they all live in the same class — so they share tests, they share dependencies, and they often share state. ### Why this matters - **Hard to test**: to test `total`, you might end up loading PDF libraries or stubbing the mailer. - **Hard to reuse**: you can't ask `Invoice` to render a PDF without also pulling in mail logic. - **Hard to change**: a small change to one responsibility risks the others — code review is slower because reviewers have to think about all three. ### The fix (preview) Split each job into its own class. `Invoice` keeps the money. A separate `InvoiceRenderer` does PDFs. A separate `InvoiceMailer` does delivery. The next lesson walks through that refactor. {% endcapture %} {{ lesson_body | markdownify }}
