Interface segregation

{% capture lesson_body %} ## Interface segregation *No client should be forced to depend on methods it does not use.* When one class exposes a fat interface — say, twenty methods — and a caller only needs three of them, the caller is still coupled to all twenty. If any of the unused methods change names or signatures, the caller's tests may break or its mock setup may rot. ### The smell ```ruby class FileStore def read(path); end def write(path, data); end def delete(path); end def lock(path); end def unlock(path); end def metadata(path); end def archive(path); end def restore(path); end def quota_used; end def quota_total; end def gc!; end # ... end ``` Anyone who just needs to `read` and `write` has to know about lock, archive, gc — at least in tests, where they may need to stub or mock. ### The cure: split by role Group methods by the **role** a caller plays. Different callers see different roles: ```ruby module Readable def read(path); end end module Writable def write(path, data); end def delete(path); end end module Lockable def lock(path); end def unlock(path); end end class FileStore include Readable include Writable include Lockable end ``` Now a caller can declare it depends on just `Readable`. If a test needs a fake store, it only has to implement `read`. ### Why it matters - **Smaller blast radius** when implementations change. - **Better tests** — easier to fake just the part you need. - **Clearer documentation** — the modules name *what* a caller actually uses. ### Pitfall: don't over-split If a caller really does use ten methods, splitting them into ten one-method modules is theatre, not design. Segregate when there are **distinct callers** with **distinct usage shapes**. Otherwise, leave the API together. {% endcapture %} {{ lesson_body | markdownify }}
