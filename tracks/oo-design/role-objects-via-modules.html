Role objects via modules

{% capture lesson_body %} ## Role objects via modules When two unrelated classes need the **same** behavior, you have three choices: copy the code, give them a common parent, or extract a module. The module option is almost always the right one. ### What's a role? A **role** is a *capability* an object has — not what it *is*. A `User` is not a "Schedulable", but it can be *scheduled*. A `Robot` isn't a "Greetable", but it can *greet*. Roles describe what an object can *do*, not what it *is*. Inheritance answers "what is this?". Modules-as-roles answer "what can this do?". ### A concrete refactor Suppose three classes — `User`, `Robot`, and `Bot` — all need to greet. They have no other common behavior. Inheritance would force a fake `Greeter` parent class and a brittle hierarchy. A module is cleaner: ```ruby module Greetable def greet "hi, I'm #{name}" end end class User include Greetable attr_reader :name def initialize(name); @name = name; end end class Robot include Greetable attr_reader :name def initialize(name); @name = name; end end ``` `Greetable` describes the role. `User` and `Robot` opt in. They keep their own (different) responsibilities; the shared role lives in one place. ### Naming the role Good role names are usually adjectives or "-able" / "-ing" forms: `Comparable`, `Enumerable`, `Greetable`, `Trackable`, `Scheduling`. This signals "this is a capability, not a thing." ### Why a role, not a parent? Inheritance fixes the relationship at definition time. A `Cat` cannot become a `Dog`. Roles are more flexible — an object can play many roles, and Ruby allows mixing several modules in. You can also add a role to a single instance with `obj.extend(Role)`. ### Pitfall: roles that need state Modules can define methods but they share the host class's instance variables. Always document what state a role expects. If the role needs lots of its own state, it probably wants to be a separate object you compose with, not a module you mix in. ### Rule of thumb - Same-shape capability across **unrelated** classes → module. - Specialization of a real **is-a** relationship → inheritance. - Heavy state of its own + reusable elsewhere → composition. {% endcapture %} {{ lesson_body | markdownify }}
