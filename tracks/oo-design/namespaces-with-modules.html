Namespaces with modules

{% capture lesson_body %} ## Namespaces with modules A Ruby **module** has two distinct uses: grouping related things under a namespace, or mixing behavior into classes. This lesson covers the first. ### What's a namespace? When two libraries define a class called `Logger`, you have a name collision — whichever is loaded last wins, silently overwriting the other. Wrapping each in a module gives them distinct, qualified names: ```ruby module Payments class Logger def log(msg); "[payments] #{msg}"; end end end module Shipping class Logger def log(msg); "[shipping] #{msg}"; end end end Payments::Logger.new.log("ok") # "[payments] ok" Shipping::Logger.new.log("ok") # "[shipping] ok" ``` `Payments::Logger` reads "the Logger inside the Payments namespace." `::` is how you walk into a namespace. ### Nesting Modules can nest as deep as you need: ```ruby module Acme module Billing class Invoice; end end end Acme::Billing::Invoice.new ``` ### Why use them? - **Avoid collisions.** Two libraries can both define `User` without fighting. - **Group related code.** Everything billing-related lives under `Acme::Billing`. - **Convey intent.** Reading `Payments::Logger.new` tells the reader immediately what kind of logger this is. ### Constants live in modules too Constants — including class names — defined inside a module are scoped to that module: ```ruby module Auth DEFAULT_REALM = "users" end Auth::DEFAULT_REALM # => "users" DEFAULT_REALM # NameError ``` ### Modules are objects In Ruby, a module is a regular object (an instance of `Module`). That means you can pass it around, ask its name, and so on: ```ruby Payments.name # => "Payments" ``` {% endcapture %} {{ lesson_body | markdownify }}
