The Comparable module

{% capture lesson_body %} ## The Comparable module When you have a class whose instances have a natural ordering — by price, by length, by score — Ruby's standard library gives you a way to plug into all the comparison methods at once: include `Comparable` and define `<=>`. ### The deal You implement **one** method: ```ruby def <=>(other) # return -1, 0, or 1 end ``` In return, `Comparable` gives your class **all** of these: - `<`, `<=`, `>`, `>=` - `==` - `between?(a, b)` - `clamp(a, b)` Plus your objects become sortable with `.sort`. ### Concrete example ```ruby class Score include Comparable attr_reader :value def initialize(value); @value = value; end def <=>(other) value <=> other.value end end a = Score.new(80) b = Score.new(95) a < b # => true a.between?(Score.new(50), Score.new(100)) # => true [b, a].sort # => [a, b] (sorted ascending) ``` All eight comparison methods came from one `<=>` definition. ### `<=>` should return -1, 0, 1 — or nil Return `nil` from `<=>` when the comparison is meaningless (apples and oranges literally). Methods like `<` then return `nil`, and callers get a clear signal that the values aren't comparable. ### Why it matters for design Including `Comparable` is a way to **buy a lot of behavior cheaply**. Instead of writing seven comparison methods (and forgetting one), you write one and get them all consistently. That's the payoff of including well-designed standard-library modules. ### Pitfall: equality and hashing If you redefine equality (`==` or `<=>`), think about whether `eql?` and `hash` should also be redefined. Two objects that are `==` should ideally also have the same `hash`, or hash-based collections (`Set`, `Hash` keys) misbehave. {% endcapture %} {{ lesson_body | markdownify }}
