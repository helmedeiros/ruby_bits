Mixin with extend

{% capture lesson_body %} ## Mixin with `extend` `include` adds module methods as **instance** methods of the host class. `extend` adds them as **class** (singleton) methods. ### Side-by-side comparison ```ruby module Counter def count; @count ||= 0; end def bump; @count = count + 1; end end class WithInclude include Counter # available on instances end class WithExtend extend Counter # available on the class itself end WithInclude.new.bump # works: instance method WithExtend.bump # works: class method WithInclude.bump # NoMethodError WithExtend.new.bump # NoMethodError ``` ### When to use each - **`include`** — the module describes a *role* of instances: "anything that can be Greetable, Comparable, Enumerable…". This is the common case. - **`extend`** — the module describes class-level helpers: factory methods, registries, configuration DSL. ### `extend` on a single object You can also `extend` an individual object — adding methods to *that instance only*: ```ruby module Yelling def speak; "HEY!"; end end obj = Object.new obj.extend(Yelling) obj.speak # => "HEY!" Object.new.speak # NoMethodError — another instance is untouched ``` This is rarely needed but handy for test doubles and one-off patches. ### `include` + `extend` together (the Concern pattern) A common pattern is to use both: `include` adds instance methods, while a nested `ClassMethods` submodule is `extend`ed to add class methods: ```ruby module Trackable def self.included(base) base.extend(ClassMethods) end def track!; @tracked = true; end # instance method module ClassMethods def tracked_count; @tracked_count ||= 0; end end end ``` `ActiveSupport::Concern` automates the boilerplate, but this is what it's doing under the hood. {% endcapture %} {{ lesson_body | markdownify }}
